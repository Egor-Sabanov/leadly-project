# Внешний монитор LEADLY

Монитор проверяет опубликованный `/api/status` с GitHub Actions, независимо от Vercel и Supabase. Endpoint возвращает только общий статус и время; проверяет Auth, историю импорта и включённое расписание 10 минут. Не раскрывает аккаунты, задания, ключи или журналы.

При сбое выполняется повторная проверка. Сообщение отправляется владельцу через проверенный @leadly_work_bot при смене состояния; напоминание об одном сбое — не чаще 6 часов. Есть сообщение о восстановлении, сохранение состояния, обработка 429 и неопределённой отправки. Успешные проверки не создают сообщений.

## Однократное включение владельцем

1. В GitHub репозитория Egor-Sabanov/leadly-project открой Settings → Secrets and variables → Actions → New repository secret.
2. Сохрани `TELEGRAM_BOT_TOKEN`: существующий токен @leadly_work_bot из BotFather. Не отправляй его в чат и не добавляй в исходники.
3. Открой в своём вошедшем аккаунте https://leadly-topaz-seven.vercel.app/api/operations/monitor-recipient . Endpoint доступен только настроенному оператору и показывает только его собственный подтверждённый ID чата. Сохрани `chatId` в GitHub как секрет `TELEGRAM_CHAT_ID`.
4. Проверь и объедини отдельный PR мониторинга в default branch. Рабочий код приложения из leadly-mvp-download этим PR не заменяется.
5. В Actions → LEADLY external monitor → Run workflow включи `test`. Одно служебное сообщение должно прийти владельцу. Затем дождись запуска по времени и проверь успешный итог.

Текущая GitHub-интеграция агента не имеет доступа к Actions Secrets (HTTP403), поэтому она не может выполнить шаги 2–3 вместо владельца. Правило проекта оставляет main неизменным без отдельного решения владельца: PR подготавливается для проверки, автоматически не объединяется.

Расписание — каждые 5 минут со сдвигом от круглого часа. GitHub Actions может задерживать расписание; это не гарантия точного времени. Публичные репозитории могут терять активное расписание после 60 дней без активности — это нужно контролировать. Для большей гарантии впоследствии использовать отдельный uptime-сервис. Пока owner secrets, объединение и настоящий запуск не подтверждены, монитор считается подготовленным, а не включённым.

Состояние хранится в GitHub Actions Cache без секретов и персональных данных. Сохраняется только state.json; lock не кешируется. Не очищать кеш регулярно: это сбрасывает защиту от повторных предупреждений. При аварийном сбросе одно повторное предупреждение возможно. Локальный запуск допускается с явными секретами окружения; скрипт никогда их не печатает.
