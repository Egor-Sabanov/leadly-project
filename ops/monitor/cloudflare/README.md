# Отдельный монитор владельца

22 октября GitHub показал пять успешных плановых проверок за ночь с перерывами до пяти часов, хотя задан интервал пять минут. Бэкап также запустился почти на пять часов позже. Лента Supabase при этом продолжала обновляться каждые десять минут. GitHub Actions оставлен для резервных копий; его расписание нельзя считать быстрым обнаружением остановки сайта.

Этот Worker проверяет публичный `/api/status` независимо от Vercel и Supabase. Он использует тот же механизм уведомлений, что CLI-монитор: повторная проверка, проверка имени бота, одно сообщение о сбое/восстановлении, паузы Telegram и сохранение неопределённой отправки перед повторным запуском. Состояние хранит один SQLite Durable Object. Перекрывающиеся проверки объединяются. Публичные HTTP-маршруты выключены; отправка доступна только плановому событию через закрытый binding.

## Контроль резервной копии

После публикации этого изменения тот же Worker читает публичную GitHub Actions metadata только собственного Egor-Sabanov/leadly-project/workflow backup.yml/main. Никакие дополнительные GitHub credentials не нужны, пока repository публичный. Метаданные обновляются раз в15мин; возраст snapshot пересчитывается при каждом пятиминутном tick. На пересечении срока свежести перед предупреждением выполняется новое чтение. При rate limit сохраняется пауза провайдера; при кратком отказе API используется ранее проверенная копия, но после часа без успешной проверки приходит отдельное предупреждение.

Для зелёного backup нужны успешные snapshot/restore/encrypt и upload шаги, непустой неистёкший artifact с ожидаемым именем, соответствующим run/branch/commit. Возраст считается от начала сбора данных, не от загрузки архива. Проверяются metadata и успешные шаги проверенного workflow; Worker не скачивает и не расшифровывает архив. Ошибка/пропуск job, отсутствующий/неподтверждённый архив, ожидание дольше часа или копия старше24ч требуют внимания. Новый workflow запускает копирование два раза в сутки с запасом до порога24ч; расписание GitHub остаётся best effort.

Сайт и backup используют один поток уведомлений: сообщение объясняет каждую неисправную часть, частичное и полное восстановление. Существующий state, Telegram retry_after, неопределённая доставка и лимит повторов6ч сохраняются. Новая здоровая backup-проверка не повторяет уже отправленное предупреждение о сайте. Публичных маршрутов запуска или сброса состояния нет; старый Durable Object ID не меняется.

Deploy workflow после публикации ожидает естественный cron tick через Wrangler tail и подтверждает новое backup-чтение. Каждый release ID обновляет только кэш публичных метаданных, сохраняя состояние уведомлений и Telegram-паузы. Действующая пауза GitHub rate limit также сохраняется при обновлении. Служебный журнал содержит только фиксированный backupError и время backupNextCheckAt, без ответа API или ключей. Workflow не вызывает публичный тестовый endpoint. Если наблюдение не удалось, вывод отдельно сообщает deployed=true/observationVerified=false: уже опубликованный Worker не считается автоматически откатанным. Без setup_test=true новый активационный текст владельцу не отправляется.

## Подключение

1. Создать аккаунт https://dash.cloudflare.com/sign-up и подтвердить почту. Домен не требуется.
2. В https://dash.cloudflare.com/profile/api-tokens создать API token по шаблону **Edit Cloudflare Workers**, ограничив ресурсы своим аккаунтом. Сохранить токен в GitHub Actions Secret `CLOUDFLARE_API_TOKEN`. Не передавать токен в чат или исходники.
3. Токен должен позволять читать выбранный аккаунт и публиковать Workers, включая Durable Object. Если доступно несколько аккаунтов, сохранить нужный несекретный 32-символьный Account ID в Repository variable `CLOUDFLARE_ACCOUNT_ID`. Код отказывается выбирать из нескольких аккаунтов самостоятельно.
4. Проверить отдельный operations PR и получить решение владельца об объединении. Workflow `.github/workflows/cloudflare-monitor.yml` запускается только вручную и не публикует приложение LEADLY.
5. Запустить **Deploy LEADLY owner monitor**, для первого запуска явно выбрать `setup_test=true`. Workflow использует уже настроенные `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Новые копирования этих значений владельцем не нужны.
6. Workflow проверяет общую логику, защиту публикации, dry-run bundle и настоящий локальный Workers runtime. При первой публикации создаёт Worker без расписания, сохраняет секреты через stdin Wrangler, затем включает cron. При обновлении сохраняет действующее расписание до финального deployment. Вывод CLI не публикуется: доступны только фиксированные коды ошибок.
7. В Cloudflare → Worker `leadly-owner-monitor` проверить Cron Trigger `*/5 * * * *`, три последовательных естественных запуска и записи `{status, notification}`. Подтвердить получение одного служебного сообщения владельцем. Разовый тест помечается использованным до отправки; повторить его можно только новым явным workflow-запуском с `setup_test=true`. Неопределённая отправка и `retry_after` не обходятся тестом.
8. После подтверждения Cloudflare отключить прежний workflow **LEADLY external monitor**, чтобы два монитора не отправляли одинаковые предупреждения. Backup workflow сохраняется. Не отключать прежнюю проверку до появления работающей замены.

Код и локальные проверки не означают, что Cloudflare уже включён. До фактических cron-запусков и получения владельцем сообщения активация остаётся открытой. Точные условия и квоты плана проверяются в кабинете перед публикацией; платный план не требуется автоматически кодом. Целевой интервал — пять минут, отдельной гарантии времени выполнения нет.

## Проверка разработчиком

`node ops/monitor/monitor.test.cjs`, `node ops/monitor/backup.test.cjs`, `node ops/monitor/cloudflare/worker.test.cjs`, `node ops/monitor/cloudflare/deploy.test.cjs`, `node ops/monitor/cloudflare/observe.test.cjs`.

Wrangler зафиксирован на `4.151.3`, устанавливается отдельно от зависимостей приложения. `wrangler deploy --dry-run --config ops/monitor/cloudflare/wrangler.jsonc --outdir /absolute/bundle/path` не публикует Worker. Для native fixture использовать Miniflare из этого закреплённого Wrangler: `NODE_PATH=/path/to/tools/node_modules node ops/monitor/cloudflare/runtime-fixture.cjs /absolute/bundle/path/worker.js`. Все внешние запросы fixture перехватываются; рабочие токены и пользователи не используются. Проверяются SQLite после перезапуска, объединение запусков и одно уведомление о сбое/восстановлении.

Во время native-проверки выявлены и исправлены ограничения Workers: класс наследует `DurableObject`, вместо Node Buffer используется TextDecoder, HTTP redirect — `manual` с отказом на 3xx. Проверка только в Node этого не доказывала.

## Следующие критерии надёжности

27 октября настоящий вход владельца и архивные данные в отдельной копии подтверждены после исправления SMTP-порта. Контроль backup подготовлен этим изменением; пока оно не объединено/не опубликовано и не наблюдался natural tick, считать его активным нельзя. Измеренное полное RTO, OAuth/домены и независимое хранение архива остаются отдельными критериями. См. [план аварийного восстановления](../../backup/DISASTER-RECOVERY.md). Не восстанавливать копию поверх рабочего проекта и не менять production `/api/status` ради проверки сбоя.
