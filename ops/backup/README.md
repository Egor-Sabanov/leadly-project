## Состав и ограничения

- Транзакционно согласованный pg_dump схем public/auth/storage, включая строки Auth, связи, функции, политики и выдачу прав. Это не JSON-выгрузка нескольких таблиц.
- Файлы всех Storage-бакетов, SHA256, пути, размеры и признаки изменений во время копирования.
- Роли для изолированной проверки создаются без паролей и права входа; RLS и grants восстанавливаются и проверяются.
- До шифрования архив БД восстанавливается в пустую локальную базу. Сверяются строки каждой таблицы, метаданные Storage и файлы. При несоответствии архив не публикуется.
- Между PostgreSQL и Storage нет общей транзакции. Если файл меняется во время копии или набор объектов не совпадает, копия отклоняется; её нужно повторить. Для аватаров приложение использует отдельные версии файлов.
- Управляемые cron/Vault/net-схемы исключены, чтобы восстановление не запустило рассылку или импорт. Расписание и секрет Vault после аварийного восстановления настраиваются отдельно.
- Настройки OAuth, SMTP, домены, переменные Vercel, секрет JWT и настройки самого хостинга не находятся в этой копии. Их нужно сохранять и восстанавливать отдельно. Восстановление строк Auth не является проверкой настоящего входа на новом Supabase-проекте.
- Restore разрешён только на localhost/127.0.0.1 и в новой пустой базе с именем leadly_restore_*. Производственный адрес отклоняется до чтения архива. Нет DROP CASCADE и восстановления поверх действующих данных.

## Однократная настройка владельцем

1. Сохранить вне рабочей среды закрытый ключ private.asc и файл passphrase.txt; публичный public.asc можно хранить в репозитории. Только публичный ключ используется в GitHub Actions. Закрытый ключ и фразу туда не загружать и в чат не отправлять.
2. Supabase → Connect → Session pooler (порт 5432): строку PostgreSQL подключения сохранить в GitHub Actions Secret `LEADLY_BACKUP_DATABASE_URL`. Пароль БД вводится только в защищённое поле GitHub. Это не service-role key и не пароль аккаунта Supabase.
3. Существующий серверный ключ проекта сохранить в Actions Secret `SUPABASE_SERVICE_ROLE_KEY`; URL проекта зафиксирован в workflow. Этот ключ нужен для чтения файлов Storage, не для SQL-подключения.
4. После сохранения закрытого ключа и фразы вне среды добавить Repository variable `LEADLY_BACKUP_KEY_READY` со значением `true`. Без этого резервное задание не запускается.
5. Объединить отдельный проверенный PR операций в default branch. Main не меняется агентом без решения владельца. Затем вручную запустить LEADLY encrypted backup и проверить успешное восстановление перед шифрованием и наличие artifact.
6. Скачать первый архив и выполнить полный restore с закрытым ключом в отдельной среде. Пройти настоящий вход и основные сценарии в отдельном совместимом Supabase-проекте. Только после этого пункт восстановления запуска считается закрытым.

Текущая интеграция агента не имеет разрешения на GitHub Actions Secrets (HTTP403); эти значения сохраняет владелец. Реальный SQL-доступ в облачной среде не настроен. Пока первый производственный архив и восстановление не подтверждены, не объявлять реальный backup/restore выполненным.

## Расписание и хранение

Плановый запуск — ежедневно 04:17 МСК, best-effort GitHub Actions. Целевой начальный RPO — до 24 часов; это целевое значение, пока не подтверждённое наблюдением. Время полного восстановления ещё измеряется. Хранение encrypted artifact —14 дней; архив больше 32 МБ не загружается без пересмотра ёмкости. Держать отдельную копию архива и ключа вне GitHub; artifact в одном аккаунте не гарантирует восстановление при потере аккаунта.

Результаты тестов: настоящий локальный PostgreSQL17, отдельные source/restore базы; зашифрованный round trip, защищённый фразой закрытый ключ, Auth-строки, связи, Storage и изоляция RLS проверены на собственном тестовом наборе. Это не копия живой базы LEADLY. Рабочие данные не восстанавливались поверх production.

Восстанавливать только архивы из своих проверенных workflow-запусков с известным source commit. Публичный ключ позволяет зашифровать файл любому; само успешное расшифрование не доказывает происхождение SQL. Не принимать произвольные присланные архивы как собственные резервные копии.

Локальные зависимости: Node24, клиент PostgreSQL17+, GnuPG, tar, Python3, установленный @supabase/supabase-js. Конфигурация задаётся через переменные из workflow. Вызовы: `node ops/backup/backup.cjs backup` и `node ops/backup/backup.cjs restore`. Генерация новой пары ключей: `node ops/backup/generate-key.cjs /private/path/outside/repository`.
