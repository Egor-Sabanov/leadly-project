# Аварийное восстановление LEADLY

Это порядок действий оператора. Значения ключей, пароли, закрытый ключ GPG и защитная фраза хранятся отдельно в защищённом хранилище владельца, а не в этом документе или Git.

## Текущее состояние и цели

Архив39731889214 от22 октября был расшифрован и проверен локально:68 таблиц и2 файла Storage. Собственные данные приложения и Auth затем перенесены в отдельный Supabase-проект `umexhmyeheonfsktcyqi`, системная схема платформы сохранена.27 октября владелец подтвердил настоящее письмо, отдельный пароль копии, выход/повторный вход и архивные профиль, сохранения, дела и фото. [Подробное подтверждение](https://github.com/Egor-Sabanov/leadly-project/blob/13197436b0eb9eeaa61dbf47c60d40bfcedab074/docs/RECOVERY-MAIL-2026-10-27.md).

Этот прогон не измерил полное RTO и не восстановил все OAuth/Telegram-настройки. SQL-фаза около11с и загрузка файлов около10с не являются временем полного восстановления сервиса.

Цель RPO — не более24ч пригодных данных. Для запаса workflow после установки этого изменения запускается два раза в сутки, в01:17 и13:17UTC (04:17 и16:17МСК). GitHub может задерживать расписание: контроль возраста проверенной копии обязателен. Целевое и фактическое RTO должны быть согласованы после отдельного измеренного прогона; обещать гарантированное время пока нельзя. GitHub artifact хранится14дней. Владелец отдельно сохраняет зашифрованные архивы и материалы расшифровки вне этой облачной среды.

## Порядок действий

1. **Определить происшествие.** Записать время обнаружения в UTC, состояние сайта/базы/Auth/Storage, последнюю пригодную копию и доступность провайдеров. Сохранить рабочие адреса и связи до принятого решения о переключении. Объявить пользователям только подтверждённые последствия.
2. **Выбрать архив.** Проверить собственный repository/workflow/main, успешные snapshot/restore/encrypt/upload шаги, непустой неистёкший artifact. Записать run ID, commit, время начала snapshot, artifact ID/срок хранения и SHA256 скачанного зашифрованного файла. Подписанные download URL не сохранять в документах.
3. **Проверить расшифровку локально.** Использовать приватный ключ/фразу через штатный GPG. Не печатать их и не загружать в GitHub. В новой временной локальной PostgreSQL проверить архив и Storage штатным localhost-only restore. При несоответствии остановиться и выбрать другой проверенный архив. Очистить временные plaintext/DB после проверки.
4. **Подготовить пустую отдельную цель.** Сравнить управляемые столбцы, ограничения, роли, функции, triggers, policies и extensions. Проверить нулевые пользовательские данные. Занятая цель означает остановку. Нынешняя recovery-цель уже содержит проверенные данные; повторный перенос в неё запрещён. Пауза/очистка проекта и платные ресурсы требуют отдельного решения владельца.
5. **Перенести собственные данные.** Использовать отдельный исполнитель с allowlist ref, empty guard, транзакцией, проверкой counts/hashes до COMMIT и после него. Не заменять системные Auth/Storage DDL или migration ledgers. Исключить старые sessions/refresh/one-time tokens, cron/Vault/net, leases и очередь уведомлений. Проверить rollback на несовместимости до настоящей записи.
6. **Восстановить файлы.** Приватные buckets и policies, загрузка без перезаписи; скачивание и сверка размера/SHA256. Не превращать bucket в публичный ради проверки.
7. **Поднять закрытое приложение.** Использовать URL/публичный и service-role key именно новой цели. Server key в проверочной копии только Preview; Vercel Authentication ALL. Импорт/автоуведомления выключены, webhook рабочего бота сохраняется. Проверить сборку, guest401 и изоляцию технических аккаунтов, затем удалить только свои fixtures.
8. **Настроить почту и вход.** Site URL должен указывать на нужный deployment, callback должен быть разрешён. Для Gmail — smtp.gmail.com, **587/STARTTLS**, sender и username согласованы, отдельный App Password из хранилища владельца. Опечатка578 вызывала серверный таймаут в реальном прогоне. Установить проверенные Subject/HTML, затем один обычный запрос письма самим участником. Участник вводит пароль/код у себя, выходит и входит заново, сверяет прежние данные. Агент не создаёт ему административную сессию или magic link.
9. **Восстановить внешнюю конфигурацию.** OAuth callback нового Supabase разрешается в консоли соответствующего провайдера; копирование SQL само по себе Google/VK/Яндекс не включает. Telegram/Mini App/webhook и ограничения Deployment Protection требуют отдельного согласованного плана. Не снимать защиту всей копии ради доступности webhook. Для контрольного health при необходимости установить пустой pg_cron:jobs0/scheduler disabled; degraded в такой копии ожидаем и не означает поломку Auth.
10. **Принять решение о переключении.** Предъявить конкретный target/deployment, результаты проверок и план обратного переключения. Только после решения владельца менять рабочие aliases/webhook, новые Vault/cron grants и подключать импорт. В восстановленной базе функции включения импорта намеренно отозваны, уведомления выключены; одного вызова старого enable RPC недостаточно. Использовать актуальный проверенный installer/release и новые секреты цели.
11. **Проверить работу после переключения.** Сайт/Auth/Storage, реальные разрешённые способы входа, актуальный импорт, персональные данные, бот/Mini App, отписка и отсутствие повторов. Внешний монитор должен увидеть новую успешную копию и актуальную проверку сайта. Старую цель сохранять до согласованного окончания окна возврата; не направлять новые записи одновременно в две базы без отдельного плана.

## Что записать по итогам

Время обнаружения, начало восстановления, завершение SQL, завершение файлов, готовность конфигурации, первый реальный вход, проверку пользовательских сценариев, момент переключения и восстановления наблюдения. Отдельно — время snapshot пригодного архива и фактическую потерю данных. Общее RTO считается до работающего сервиса и проверенных внешних функций, а не только до COMMIT.

Критерии приёмки: данные/права/файлы проверены, добровольный участник вошёл своим способом, внешняя конфигурация подтверждена, импорт и сообщения не дублируются, монитор и новая копия работают. Открытые пункты остаются явно открытыми. Этот документ — план; он не объявляет повторное учение или переключение уже выполненным.
