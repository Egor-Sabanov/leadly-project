# Живая проверка базы LEADLY

19 октября 2026 года, по Москве.

## Подтверждённый результат

SQL обновления применён владельцем в Supabase. Серверный API подтверждает новые RPC `leadly_save_profile`, `leadly_update_opportunity`, `leadly_reserve_ai`, поле `profiles.requested_plan` и таблицу `leadly_ai_requests`. Подготовленный SQL и локальные тесты описаны в DATABASE-UPDATE.md.

Через **настоящие Supabase Auth и REST API** выполнены 24 успешные проверки, используя два созданных для этого запуска временных аккаунта:

1. Создание двух подтверждённых тестовых аккаунтов и вход по паролю через Auth API. Admin API использовал `email_confirm=true`, без отправки почтовых сообщений.
2. Существующий регистрационный триггер создал отдельный профиль каждому аккаунту с прежним начальным `Europe/Chisinau`.
3. RPC сохранил профиль, навыки, цель, типы возможностей и выбранную временную зону каждого пользователя. После повторного входа данные сохранились.
4. Второй аккаунт не смог прочитать или изменить профиль первого. Интерес к AGENCY сохранился как поле профиля; списаний и активации платных прав нет.
5. Сохранились флаг избранного, заметка и статус задания. Повторная запись того же статуса не добавила лишнюю историю. У второго аккаунта состояние того же задания независимое.
6. Чужая воронка недоступна; подстановка чужого user_id при вставке отклонена. Анонимный вызов workflow RPC запрещён.
7. Создание, чтение, смена статуса и удаление собственного клиента работают; другой аккаунт клиента не видит.
8. Финансовая запись скрыта от другого аккаунта. Удалить чужую запись нельзя, удаление собственной после новой политики работает.
9. Черновик отклика сохраняется в истории; другой аккаунт не получает доступ к нему.
10. Пользовательский токен не может вызывать серверное резервирование AI. Серверный вызов разрешает 20 попыток и отклоняет 21-ю. OpenAI не вызывался, платной генерации не было.
11. Созданные тестом аккаунты и строки удалены; счётчики затронутых таблиц вернулись к исходным значениям. Существующие аккаунты и задания не изменялись.

Статусы/заметки проверялись в личных строках временных пользователей на существующем задании; глобальная запись задания не менялась. Удаление аккаунтов ограничивалось сохранёнными ID и проверкой уникального `leadly_validation_run` в метаданных. При ошибках промежуточных тестов также выполнена очистка с проверкой исходных счётчиков.

Приватный итог полного API-запуска сохранён вне GitHub: `/workspace/leadly-artifacts/live-db-validation-500d3342571044efbec7af2fb0dca972.json`. В нём нет паролей, JWT или ключей. Остальные диагностические отчёты также находятся только в `leadly-artifacts`. Временные пароли/токены передавались в памяти, не в аргументах команд и не в исходниках.

## Пределы проверки

Это API-интеграционные проверки. Они **не подтверждают** доставку почты/восстановление через SMTP, Google/VK/Яндекс OAuth, платную AI-генерацию, платежи, импорт источников, работу Mini App или пользовательского Telegram-бота.

Прямая браузерная проверка входа в облачном Chromium остановилась до входа: `net::ERR_CERT_AUTHORITY_INVALID` при обращении к Supabase через прокси среды. Серверные и Python API-запросы проходят с действующей проверкой TLS. Настоящий Chromium-login пока нельзя объявлять успешным.

Попытка добавить уже установленный CA облачного прокси в общий NSS Chromium была отклонена автоматической проверкой разрешений: это расширяет доверие браузера для всех HTTPS-сайтов и требует явного разрешения пользователя. Изменение **не выполнено**. Сертификат не добавлен в глобальное хранилище, TLS-проверки не отключались. Временное неиспользуемое хранилище внутри workspace удалено. Прямую браузерную проверку продолжать только после разрешённого решения вопроса доверия.

Предыдущие 198 локальных тестов, lint/build и 16 изолированных browser-проверок остаются историческими результатами. Они не подменяют этот live API-запуск и не превращают неуспешный Chromium-login в успешный тест.

## Плагин и дальнейшая самостоятельная работа

Пользователь установил плагин Supabase и попросил выполнять доступную работу самостоятельно, собирая необходимые действия владельца к концу. В текущем доступном наборе инструментов нет Supabase SQL/MCP-методов, Management API token или PostgreSQL connection string. Работа выполнена через уже авторизованный API. Не заявлять прямое SQL-управление по одному наличию плагина у пользователя.

Следующие изменения DDL готовить и проверять самостоятельно; если прямой SQL-доступ не появится, собирать их в один проверенный bundle для выполнения владельцем. Отдельно остаются внешние настройки Google/социальных провайдеров, публичный HTTPS-хостинг и токен/разрешения Telegram-бота. Mini App, полноценный бот и дальнейшая работа над визуалом обязательны и не объявляются завершёнными.
