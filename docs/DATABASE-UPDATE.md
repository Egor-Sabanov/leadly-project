# Обновление базы по аудиту владельца

19 октября 2026 года, по Москве. Этот документ описывает подготовленное обновление; он не подтверждает выполнение SQL в живом Supabase.

## Результаты аудита

Из предоставленного владельцем отчёта SQL Editor:

- RLS включён на всех 24 public-таблицах. Политики личных записей используют `auth.uid()` и владельца строки. Наличие RLS само по себе не заменяет сквозной тест с двумя аккаунтами.
- Существующий триггер `auth.users.on_auth_user_created` вызывает `public.handle_new_user()`, создаёт профиль и использует `Europe/Chisinau`. Он сохраняется вместе с определением функции и прежними настройками.
- В профиле уже есть `skills_summary`; нет `requested_plan`. Workflow-функций `leadly_save_profile`, `leadly_update_opportunity`, `leadly_reserve_ai` и таблицы квоты AI пока нет.
- В live transactions есть SELECT/INSERT-политики, но нет DELETE-политики. Подтверждённое удаление собственной операции из интерфейса поэтому не работает. UPDATE сейчас не добавляется: соответствующего редактора операций нет.
- Каталог содержит 67 навыков и 54 услуги. Название «Сценарии для видео» уже есть под другим slug. Заполнение каталога уточнено: совпадение существующего имени или slug сохраняет старую запись, не создавая повторное название. Старые дубли не удаляются.

Предыдущий резервный экспорт: 24 exposed public-таблицы, 1080 записей. Файлы и SHA-256 manifest находятся вне GitHub в `/workspace/leadly-backups/`; указатель на каталог — `/workspace/leadly-artifacts/latest-supabase-backup-path.txt`. Отчёт аудита сохранён вне checkout. REST-экспорт не является полным транзакционным дампом PostgreSQL: он не содержит Auth, Storage и полного DDL.

## Что делает обновление

Файл `supabase/ops/02_apply_audited_mvp.sql` объединяет миграции 0004, 0005 и 0006 в **одну транзакцию**. Проверяет RLS нужных таблиц и наличие ожидаемого регистрационного триггера до изменений. Сохраняет определение старого триггера/функции и сравнивает их после применения. Ошибка до COMMIT откатывает всё обновление.

Добавляются:

- отсутствующие поля профиля, атомарные RPC сохранения профиля/предпочтений и статуса/истории/заметок;
- серверная квота AI, недоступная клиентским ролям;
- недостающие навыки и услуги разных профессий с сохранением существующих записей;
- DELETE-политика для собственных финансовых операций, только для authenticated, и соответствующая табличная привилегия.

Политики остальных таблиц, имеющийся `handle_new_user`, пользовательские записи и старые настройки не заменяются. Скрипт не активирует оплату, Google OAuth, источники или Telegram. Он не выполняет исходную 0001 и не сбрасывает базу. В конце отправляет PostgREST уведомление о перечитывании схемы и возвращает `leadly_update_result`.

## Выполнение владельцем

В текущей среде есть серверный REST-ключ, но нет PostgreSQL connection string/password или Supabase Management API token. REST-ключ не предоставляет произвольный SQL. Не добавлять обходной RPC для выполнения произвольных запросов.

1. Открыть **Supabase → SQL Editor → New query**.
2. Вставить **весь** `02_apply_audited_mvp.sql` и выполнить Run один раз. Не выполнять фрагменты отдельно: атомарность обеспечивается общей транзакцией.
3. Передать результат `leadly_update_result`. Если редактор сообщает ошибку, передать её текст; не повторять исходную 0001 и не удалять таблицы.

В результате ожидаются true для всех проверочных флагов. Значения skills_count/services_count зависят от уже существующего каталога, их не надо подгонять вручную.

## Проверки и продолжение

Локальные SQL-тесты моделируют фактический существующий регистрационный триггер и недостающую DELETE-политику. Проверяются сохранность триггера/старых профилей/каталога, повторяемость всего bundle, полный откат при намеренной ошибке между миграциями, удаление собственной финансовой записи и отказ удаления чужой, а также прежние проверки RLS и квоты.

После подтверждения живого применения проверить новую схему через API и готовность приложения. Затем провести контролируемые сценарии с двумя тестовыми аккаунтами: регистрация/профиль, сохранение/статус/заметка, личные клиенты и финансы, изоляция пользователей. Тесты должны очищать только свои созданные записи/учётки и не затрагивать существующих пользователей. Живой сквозной тест пока не выполнен.

Итог локальной проверки этой подготовки: `npm run check` — lint, 198/198 тестов (включая 20 PostgreSQL/WASM), TypeScript и production build успешно. Браузерные тесты в этом шаге не повторялись: интерфейс не менялся.
