# Направления работы и источники заданий

Обновление от 18 октября 2026. Дополняет DARK-RUSSIAN-AUTH и прежний MVP-LAUNCH; не означает запуск живых интеграций.

## Профессии

В `lib/disciplines.ts` собраны 12 направлений: дизайн, разработка, тексты/редактура, маркетинг, видео/монтаж, SMM, звук/озвучка, переводы, маркетплейсы, аналитика, ассистирование, обучение. Одна и та же модель используется в профиле, onboarding, фильтре ленты, демонстрации и поиске hh.ru.

Кнопка «Использовать направление» заполняет название профессии и добавляет навыки, сохраняя введённые вручную. Это шаблон: пользователь должен оставить только свои реальные навыки и сохранить профиль. Распознавание направлений по тексту эвристическое; одно задание может относиться к нескольким направлениям. Это фильтр поверх текущей ограниченной выдачи, а не полный поиск по всей базе.

Скоринг понимает дополнительные пары названий инструментов/услуг: DaVinci Resolve/Давинчи Резолв, Premiere Pro/Премьер Про, Power BI/Пауэр Би, Wildberries/Вайлдберриз, письменный перевод/перевод текстов. Неизвестный бюджет остаётся неизвестным. Новые примеры демонстрации вымышлены и не записываются в базу.

Добавочная миграция `0005_expand_digital_catalog.sql` расширяет каталог навыков и услуг. Она не перезаписывает имеющиеся названия или пользовательские записи и проверена повторным исполнением. Для живой базы сначала проверить схему/список применённых миграций и создать резервную копию, затем применить только отсутствующие миграции. Из этой среды миграции удалённо не запускались.

## hh.ru

При пустом `LEADLY_HH_QUERY` импорт делает отдельный официальный запрос для каждого направления. Ограничения: 12 запросов, по 5 результатов, не более 3 запросов одновременно; повторы ID между направлениями пропускаются. Русский язык проверяется до записи. Итоги и ошибки отдельных направлений возвращаются планировщику отдельно.

`LEADLY_HH_DISCIPLINES=video,audio,design` ограничивает направления. Пустое значение выбирает все. Непустой `LEADLY_HH_QUERY` заменяет распределённый поиск одним пользовательским запросом до 20 записей. Если прежде был установлен общий запрос, очистить его для равномерного поиска по профессиям.

Для записи по-прежнему нужны Supabase URL, серверный ключ и `CRON_SECRET`. Публичный publishable key не даёт права выполнять импорт от имени сервера. Из-за отказа сетевого proxy `403 Forbidden` живой запрос к hh.ru не проверен.

## Kwork и другие биржи

В разделе «Источники» добавлен каталог Kwork, FL.ru, Freelance.ru и Weblancer с переходом на площадки. У этих карточек явно указано, что автосбор не подключён. Список не выдаётся за работающую интеграцию.

В этой среде не удалось проверить официальный контракт/API Kwork для получения открытых заданий покупателей. Каталог услуг продавцов нельзя подменять заказами. Не добавлялись неофициальные login/password API, выгрузка cookies или обход ограничений площадок. После получения документированного разрешённого API можно добавить отдельный адаптер; официальную разрешённую RSS-ленту можно подключить через существующий RSS-коннектор. Адреса RSS не угадываются и не активируются без проверки.

Freelancehunt API уже реализован; его включение требует токена владельца. Наличие адаптера не подтверждает доступ или успешную загрузку. Иностранные и неопределённые по языку объявления всех подключённых источников пропускаются.

## Telegram

Для первого просмотра предложены `@finder_vc`, `@distantsiya`, `@designhunters`. Это кандидаты: текущая доступность, свежесть публикаций и право подключить бота не проверены. Сеть облачной машины вернула proxy 403 при обращении к Telegram. Публикации из этих каналов не импортируются автоматически.

Официальный Bot API получает новые публикации каналов, в которые бота добавили с разрешения владельца. Он не читает историю и произвольные чужие каналы по подписке пользователя. Если владельцы выбранных каналов не дают доступ, нужен другой источник с разрешённым API/RSS; наличие публичной ссылки не является таким доступом.

Добавлена конфигурация типов по каналам:

```text
TELEGRAM_CHANNEL_RULES=[{"chatId":"-1001234567890","type":"project","name":"Разрешённые заказы"},{"chatId":"-1009876543210","type":"job","name":"Разрешённые вакансии"}]
```

В примере фиктивные ID. Использовать реальные ID после предоставления боту доступа. Допускается до 50 уникальных каналов, типы `project`, `job`, `client`. Некорректный JSON/ID/тип отклоняется без перехода к менее строгим настройкам. Если переменная пуста, прежние `TELEGRAM_ALLOWED_CHAT_IDS` и `TELEGRAM_OPPORTUNITY_TYPE` продолжают работать.

В защищённых настройках или игнорируемом `.env.local` нужны `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` (32–256 символов A–Z, a–z, 0–9, _ или -), публичный HTTPS `LEADLY_SITE_URL`, разрешённые каналы и серверный ключ Supabase. Для токена в URL Bot API и локального сравнения webhook-secret нужны реальные значения в процессе, не proxy-only placeholders. Секреты не передаются в чат, git или архив.

Проверить бота, публичность каналов и его права без изменения webhook:

```bash
npm run telegram:setup -- --check
```

Зарегистрировать webhook после успешной проверки:

```bash
npm run telegram:setup -- --apply
```

Скрипт работает только с `api.telegram.org`, проверяет каждый канал и доступ бота до записи, регистрирует только `channel_post`, сохраняет pending updates и не выводит токен. Проверяет ответ `getWebhookInfo`. Запуск с `--apply` меняет webhook данного бота — использовать выделенного бота LEADLY. В текущей среде выполнена только проверка отсутствующих настроек: она завершилась ошибкой о недостающем BOT_TOKEN, а не ложным успехом. Реальной регистрации не было.

После настройки опубликовать тестовое русское задание в разрешённом канале и проверить оригинальную ссылку, тип, направление, повторную доставку без дубля и отказ для английского текста/неразрешённого канала. Импорт не отправляет пользователям уведомления.

## Supabase и фактическое состояние

Предоставленный пользователем адрес `/rest/v1/` приведён к origin `https://leezcyaqhozguvcehcpd.supabase.co`. Origin и предоставленный публичный publishable key добавлены только в игнорируемый `.env.local` с правами 0600, не в код, git или ZIP. Существующие секреты и база не изменены.

Попытки проверить `/auth/v1/settings` и `/rest/v1/` с публичным ключом остановлены proxy: `Tunnel connection failed: 403 Forbidden`. Это не ответ Supabase и не доказательство неправильного ключа. Проверить схему, провайдеров Google/GitHub и настоящий вход пока нельзя. Точный Supabase host добавлен в сохранённый черновик сети; сохранение черновика не применяет сеть к текущему процессу. Настройки надо сохранить и опубликовать через настройки среды, затем повторить проверку.

Google OAuth Client ID/Secret по-прежнему задаются владельцем в Supabase Auth. Публичный ключ проекта не предоставляет административный доступ к OAuth-провайдерам. Инструкции callback остаются в DARK-RUSSIAN-AUTH.
