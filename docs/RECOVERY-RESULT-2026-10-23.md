## Ошибка кеширования фото

Hosted-проверка выявила сохранение старого изображения в CDN после замены и даже удаления. Подтверждено, что после удаления указатель профиля был очищен, объекта в Storage не было, а API всё ещё возвращал старые байты, в том числе с новым клиентским query. Причина и подход к обходу CDN согласуются с [документацией Supabase](https://supabase.com/docs/guides/storage/cdn/smart-cdn).

В подготовленном исправлении GET сверяет состояние своего профиля перед Storage. При отсутствии avatar_url он сразу возвращает404. Запрос download использует отдельную версию из SHA256 сохранённого указателя и cache:no-store. Клиентский query не определяет версию. Настоящий hosted-прогон подтвердил новое фото сразу после замены и404 сразу после удаления.

Добавлены десять регрессионных тестов с CDN, сохраняющим старые ответы. Новый код проходит; исходный действительно падает на замене фото. Тесты проверяют ETag, удаление, отсутствие профиля, ошибку чтения, отсутствие авторизации и повторную загрузку; исходящих запросов0. После завершения паузы полный текущий `npm run check` (включая новый test:assets, lint и production build) прошёл. GitHub CI39873352732 на точном source SUCCESS, включая UI.

Исправление опубликовано на рабочий сайт: source `a2cdf44fce5735587b238c1aa598c86d1b7349b4`, READY `dpl_G34JGhe6mT34s6MzkqBB8PE5dBmp`, Next16.4.2. Сверены335 исходных файлов; прежний alias, конфигурация, основной checkout и main сохранены. После публикации прошли13 public deployment-проверок и7 настоящих avatar-проверок на собственном временном аккаунте: upload/read, Origin403, немедленная замена через новый и старый URL, ETag304, delete→404 с очисткой указателя/объекта, отзыв доступа401 после удаления fixture.
