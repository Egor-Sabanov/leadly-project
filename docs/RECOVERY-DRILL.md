# Проверка аварийного восстановления

Настоящий production-архив уже восстановлен локально:68 таблиц и2 файла. Следующая цель — подтвердить работающий вход и данные в отдельном совместимом Supabase-проекте и измерить время восстановления. Этот документ — порядок подготовки; hosted restore пока не выполнен.

## Почему нужен отдельный этап

Текущий `ops/backup/backup.cjs restore` принимает только новую пустую локальную базу. Свежий управляемый Supabase уже содержит системные Auth/Storage-таблицы и роли. Снимать защиту localhost и запускать существующий full pg_restore на такой проект нельзя: сначала требуется сравнить управляемую схему, выделить собственный DDL и подготовить перенос данных.

[Официальная инструкция Supabase](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore), прочитанная22 октября, отдельно рассматривает роли, схему, данные, изменения auth/storage и отключение триггеров во время восстановления. Она использует специально подготовленный Supabase CLI dump; наш проверенный custom pg_dump не следует считать тождественным этим файлам. Слепое копирование команд инструкции на наш архив не подготовлено к исполнению.

## Подготовка до любых записей

1. Создать отдельный проект для учений и записать его новый ref. Он должен отличаться от рабочего `leezcyaqhozguvcehcpd`. Перед созданием проверить доступный план и лимит проектов в кабинете; создание платного ресурса требует отдельного решения владельца.
2. Снять read-only инвентаризацию нового проекта: [inspect-recovery-target.sql](../supabase/ops/inspect-recovery-target.sql). В ней только версия, структура, расширения и агрегированные счётчики. Проверить пустые auth.users, storage.objects и отсутствие пользовательских объектов public. Наличие каких-либо данных означает остановку до отдельного разбора.
3. Выбрать архив только из своего успешного workflow с проверенным source commit и artifact. Сохранить SHA256 зашифрованного файла; работать с закрытым ключом через GPG, не печатать ключ/фразу и не загружать их в GitHub Secrets.
4. Восстановить выбранный архив в новой локальной БД штатным защищённым инструментом. Сравнить типы и обязательные столбцы Auth/Storage с целью, необходимые extensions, роли, собственные функции/триггеры/RLS/grants. При отличиях подготовить явное совместимое преобразование. Не перезаписывать системные объекты без проверенного плана.
5. Только после сравнения собрать отдельный target-bound план/исполнитель с allowlist нового ref, проверкой пустоты и транзакциями. Он должен исключать cron/Vault/net и любые автоматические отправки. Точный SQL и обратный ход предъявляются к проверке до записи. Готового универсального hosted-executor сейчас нет.

## Изолированное приложение

Создать отдельный deployment с URL/ключами нового Supabase. Доступ к учениям ограничить участниками; восстановленные личные данные не публиковать. Рабочий alias LEADLY, Telegram webhook и Site URL рабочего проекта сохраняются.

В новом проекте импорт и рассылки остаются выключены. Для первичной проверки достаточно входа по паролю существующего добровольного участника и доступа к его восстановленным данным; пароль вводит участник. OAuth-проверки потребуют отдельных разрешённых redirect URLs и настроек провайдеров. SMTP, JWT, домены, переменные Vercel и Vault не восстанавливаются из этого архива автоматически.

Проверить вход/выход/повторный вход, профиль, сохранения, проекты, клиентов, задачи, финансы, два реальных Storage-файла, RLS и изоляцию второго аккаунта. Оригинальные аккаунты и связи в production не менять. После учений удалить отдельные данные/deployment по согласованному плану; архив и доказательства хранить по правилам резервирования.
