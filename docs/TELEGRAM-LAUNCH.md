# Telegram Mini App и бот LEADLY

Приложение: https://leadly-topaz-seven.vercel.app/telegram . Бот владельца: https://t.me/leadly_work_bot . Публичный вход не требует установки приложения. Mini App использует существующие возможности, профиль, задачи и воронку; отдельную базу пользователей не создаёт.

## Подключение пользователем

1. Войти в LEADLY на сайте через Google или подтверждённую почту, открыть «Профиль» → Telegram.
2. Отметить согласие на дополнительный способ входа и нажать «Подключить Telegram».
3. Открыть выданную ссылку на бота, нажать Start. Ссылка действует пять минут; повторная выдача заменяет предыдущую.
4. Вернуться именно в свой профиль LEADLY, проверить показанный Telegram и нажать «Подтвердить этот Telegram».
5. В боте открыть меню LEADLY или отправить `/app`. Mini App проверит подпись Telegram и покажет, под каким аккаунтом продолжить. После нажатия появится фирменное приветствие и рабочий экран.

Первый вход в Mini App требует связанного существующего аккаунта. Это предотвращает незаметное создание дубликатов и привязку по одному публичному имени. Если встроенный браузер блокирует cookies, экран предложит открыть сайт в обычном браузере. Для отключения есть действие в профиле и команда `/stop`; существующие сессии LEADLY при этом не завершаются, новый Telegram-вход становится недоступен.

## Команды

`/start`, `/app` открывают приложение. `/opportunities`, `/tasks`, `/profile` открывают нужный раздел после проверки входа. `/help` объясняет подключение, `/privacy` описывает данные, `/stop` отключает связь. Бот обрабатывает команды только в личном чате с самим отправителем. Неизвестные сообщения и группы игнорируются. Автоматические уведомления и рассылки пока не реализованы; настройка предпочтения в профиле не означает отправку сообщений.

## Серверные настройки

Владелец применил `supabase/migrations/0007_telegram_accounts.sql` в своём Supabase. Скрипт добавляет две таблицы и служебные функции, включает RLS и запрещает доступ клиентским ролям. Он не переносит и не удаляет существующие аккаунты, профиль или заказы. Повторное применение безопасно для созданных таблиц.

Production настроен: официальный Bot API подтвердил webhook, команды и меню @leadly_work_bot; проверенный deployment `dpl_2DQqhRoxAQHXnaCSHRzwtPung1kA`, исходники `96997116d3a2191534cfde41d494925845b92e84`. Повторная read-only проверка webhook получила совпадение URL, pending 0 и отсутствие признака последней ошибки. Настоящий запуск владельцем остаётся отдельной проверкой.

Production Vercel требует существующие Supabase URL, публичный и серверный ключи, точный `LEADLY_SITE_URL`, а также:

| Переменная | Назначение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Sensitive, только сервер. Владелец сохраняет токен BotFather напрямую в Vercel |
| `TELEGRAM_BOT_USERNAME` | `leadly_work_bot`, без @; проверяется через официальный getMe |
| `TELEGRAM_WEBHOOK_SECRET` | Sensitive, случайная строка 32–256 допустимых символов; проверка входящих обновлений |
| `TELEGRAM_SETUP_SECRET` | Отдельный sensitive секрет для служебной настройки; не передавать пользователям |

После нового deployment оператор вызывает `POST /api/telegram/setup` с Bearer setup-секретом и JSON `{"action":"check"}`, затем `{"action":"apply"}`. Перед изменениями проверяются миграция, getMe и точное имя бота. Endpoint не принимает новый токен, адрес приложения или список каналов из запроса. Он регистрирует webhook, восемь русских команд и кнопку меню LEADLY → `/telegram` через официальный Bot API. Очередь обновлений сохраняется. Ответ содержит только безопасный статус; секреты не журналируются. Setup-секрет остаётся действующим серверным секретом и может быть заменён оператором с повторным deployment; одноразовым он не является.

В локальной защищённой серверной среде альтернативно доступен `npm run telegram:setup -- --apply`; команду без `--apply` используют для чтения статуса. Не копировать токены в командную строку или исходники. Main Mini App и отдельная кнопка на странице профиля бота через BotFather не настроены; меню в чате и кнопки `/app` используют обычный официальный Web App.

## Безопасность и cookies

- Сервер проверяет HMAC подписанного initData, его единственность, размер, допустимый Telegram ID и срок не более пяти минут. `initDataUnsafe` не используется для входа.
- Связь подтверждается в две стороны: приватная команда боту только отмечает кандидата; окончательное подтверждение выполняет текущая сессия владельца профиля. На один аккаунт — один Telegram, Telegram нельзя незаметно присоединить ко второму аккаунту.
- Сервер получает подтверждённый email связанного LEADLY-аккаунта и обменивает внутренний одноразовый код через Supabase Auth. Проверяется совпадение ID на каждом шаге; письмо при таком входе не отправляется, OTP и session tokens в JSON не возвращаются.
- Первый обмен сессии требует явного нажатия под проверенной Telegram-личностью. Старый код/подпись и неподтверждённая связь не дают вход.
- Обычный сайт сохраняет Secure/SameSite=Lax. В HTTPS Mini App cookies получают Secure/SameSite=None/Partitioned; поддержка зависит от клиента. CSP разрешает встраивание только собственному origin и официальным Telegram Web origins. SDK загружается только в контексте Mini App.
- Таблицы связи, pending-запросы и функции доступны только серверной роли. Имя, ID, время связи и версия согласия нужны только для этого способа входа. Правила описаны на `/privacy`.

## Проверки перед публикацией

`npm run lint`, `npm test` (286 проверок) и production build прошли. 37 новых проверок исполняют протокол и SQL: 19 проверок подписи, срока, недоверенных запросов, обмена сессии и команд; 18 проверок настоящего PostgreSQL/WASM с RLS, ограничениями, повторным подтверждением и отключением. Официальная настройка бота проверяется отдельно с моделируемыми Bot API ответами.

Дополнительно проверена фактическая удалённая миграция и выполнены шесть интеграционных проверок настоящих Supabase DB/Auth на отдельном временном аккаунте: неподтверждённая связь не даёт вход, правильный ID получает сессию, cookies имеют нужные флаги, клиент не читает таблицу/не вызывает RPC, отключение закрывает новый вход. Подпись Telegram в этом прогоне синтетическая; это не настоящий вход с телефона. Письма не отправлялись, временный аккаунт удалён, контрольные количества таблиц восстановлены.

Адаптивные проверки используют настоящий профиль Supabase и моделируемые Telegram SDK/API, чтобы проверить состояния без чужого аккаунта Telegram. Все десять UI-сценариев прошли на ширинах 320/390/1440 px; экран входа прошёл axe WCAG A/AA без нарушений. В первом прогоне исправлен недостаточный контраст нативной кнопки, во втором — неоднозначный селектор alert в тесте (служебный announcer Next.js). Временные данные очищены после каждого прогона. Настоящий запуск на телефоне/Telegram Web, получение команд самим Telegram и переход в связанный профиль подтверждаются владельцем отдельно после настройки production.

## Задания из каналов — отдельное подключение

Mini App и личные команды работают без списка каналов. Для автоматического импорта нужны разрешение владельца публичного канала, доступ бота и явные `TELEGRAM_CHANNEL_RULES`; настройка проверит права до регистрации. Произвольные Telegram-каналы и Kwork не парсятся. Текущая лента заказов получает официальные RSS FL.ru/Freelancehunt по отдельному ежедневному расписанию; разрешённый доступ к новым источникам и уведомления остаются следующими задачами.


На опубликованном HTTPS-сайте дополнительно прошли 13 общих проверок deployment и 11 проверок страницы Mini App/серверных запретов. Служебный setup вызывается только с отдельным секретом; публичные проверки не отправляют сообщения и не создают сессий.

Шесть дополнительных production API-проверок на собственном временном аккаунте подтвердили обычную веб-сессию, доступность Telegram для нового пользователя, обязательное согласие, хранение SHA256 токена, запрет подтверждения до команды боту и отмену своего pending. Тест не открывал ссылку бота и не отправлял сообщений; fixture удалён, исходные количества восстановлены, чужие запросы сохранены.
