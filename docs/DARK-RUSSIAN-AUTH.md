## Что исправлено

## Только русскоязычные задания

`lib/opportunity-language.ts` проверяет реальный заголовок/описание, а не язык интерфейса источника, валюту или название компании. Разрешаются русскоязычные тексты с техническими названиями React/Figma/API. Иностранные, явно нерусские кириллические и неопределённые тексты не включаются. Это консервативная эвристика: короткие или смешанные русские объявления могут быть пропущены; она не объявляется безошибочным определителем языка.

Проверка применяется к RSS, Freelancehunt, hh.ru и входящим Telegram-публикациям до записи. Повторная проверка при чтении защищает выдачу от старых иностранных записей. После дополнения22 октября веб-лента и подборка бота читают весь актуальный каталог постранично. Редактор откликов получает короткую подборку и отдельно загружает выбранное задание по точному ID. AI-генерация для иностранной записи отклоняется. Наличие обработчика источника не означает предоставленный доступ к нему.

Старые записи, персональные заметки и история в базе не удаляются и не переписываются; прежние сохранённые записи могут оставаться в личной истории/воронке. Новая выдача не переводит иностранные задания под видом русских.

### hh.ru

Добавлен адаптер официального API `https://api.hh.ru/vacancies`. Он использует `locale=RU`, регион `113` (Россия), ограничение 20 вакансий за синхронизацию и запрос по digital-профессиям. Пример поддерживаемого формата проверен по официальной документации репозитория `hhru/api`, не по стороннему скрейперу.

Настройки:

```text
LEADLY_HH_ENABLED=true
LEADLY_HH_QUERY=разработчик OR дизайнер OR маркетолог OR копирайтер OR редактор OR видеомонтаж
```

Также нужны прежние серверные `SUPABASE_SERVICE_ROLE_KEY`, URL базы и `CRON_SECRET`. Планировщик вызывает защищённый `/api/cron/ingest`; при желании можно выполнить один разрешённый ручной запуск в тестовой среде. `HH_API_TOKEN` необязателен для кода и используется, только если выдан приложению и требуется провайдером. Ответы 401/403 надо диагностировать по конкретному сервису, а не обходить ограничения.

Адаптер использует только фиксированный официальный API, запрещает редиректы, ограничивает тело ответа и тайм-аут, фильтрует язык, сохраняет каноническую ссылку, тип `job`, происхождение бюджета и gross-метку. Неизвестный период оплаты не выдаётся за месячный. Повторный импорт идемпотентен.

Живые проверки hh.ru и Habr RSS в текущей облачной машине не дошли до сервисов: сетевой proxy вернул `Tunnel connection failed: 403 Forbidden`. Для hh.ru в черновике среды сохранён точный домен `api.hh.ru`; действующий доступ после сохранения настроек нужно проверить отдельно. Habr не включён автоматически и не заявляется подключённым. SQL-схема/ключи живой базы в этом экземпляре отсутствуют, реальный импорт не выполнялся.

## Google и GitHub

В приложении добавлены OAuth-маршрут `/auth/social/[provider]`, безопасный callback, проверка доступности и PKCE. У Google и GitHub нет секретов в браузерном коде. Кнопка активируется только если публичные настройки Supabase подтверждают включённого провайдера; недоступный способ входа явно выключен.

Чтобы закончить подключение, нужен проект Supabase и настройки владельца:

1. Указать URL и публичный ключ проекта в настройках среды или `.env.local` и перезапустить/пересобрать приложение.
2. В Google Cloud создать OAuth-клиент типа Web Application, настроить consent screen и разрешённую аудиторию. В Authorized redirect URIs указать **`https://<project-ref>.supabase.co/auth/v1/callback`** — это callback Supabase, он отличается от callback приложения.
3. Google Client ID и Client Secret сохранить в Supabase Auth → Providers → Google и включить провайдера. Не помещать Client Secret в `NEXT_PUBLIC_*`, архив или чат.
4. Для GitHub создать OAuth App и задать тот же callback Supabase; Client ID/Secret сохранить в Supabase Auth → Providers → GitHub.
5. В Supabase URL Configuration разрешить callback приложения **`http://localhost:3000/auth/callback`** для локальной разработки и HTTPS callback опубликованного сайта. Для восстановления оставить также прежний reset callback. Production `LEADLY_SITE_URL` должен быть точным origin своего сайта.
6. Выполнить настоящий вход/выход, отказ от авторизации, повторный вход, заполнение профиля и проверку прежнего аккаунта. Профиль предзаполняется из `display_name`, `full_name` или `name`. Привязкой/подтверждением идентичностей управляет Supabase; приложение не объединяет пользователей по неподтверждённым email.

Проверка в коде использует официальный `GET /auth/v1/settings`, а не предположение о наличии Google по установленной библиотеке. В локальном тесте проверены настоящая генерация PKCE URL/cookie библиотекой Supabase SSR и запрет произвольных redirect URL. Это не равно проверке входа в реальный Google-аккаунт.

## VK ID и Яндекс ID

Кнопки и маршруты подготовлены для custom OAuth/OIDC провайдеров Supabase; они не выдаются за включённые встроенные провайдеры. Идентификаторы по умолчанию `custom:vk` и `custom:yandex`; переопределяются серверными `LEADLY_VK_AUTH_PROVIDER` и `LEADLY_YANDEX_AUTH_PROVIDER`.

Администратор должен создать приложения у выбранных провайдеров, подтвердить их актуальную OAuth/OIDC-совместимость с custom provider конкретного Supabase Auth, настроить endpoint/issuer, scope, PKCE/nonce и mapping атрибутов по официальной документации. Специфические требования VK ID к протоколу нельзя считать выполненными по одному наличию SDK. Не отключать проверки подписи, state/nonce или PKCE ради успешного входа.

Сервер проверяет custom provider через доступный в установленном SDK Admin API, используя только серверный ключ, и передаёт в браузер лишь имя/флаг доступности. Без серверного ключа, включённого совместимого провайдера или поддержки Admin API кнопка остаётся выключенной. Живое подключение VK/Яндекс требует настроек владельца и отдельного сквозного теста; в этом чате оно не выполнено.

## Что остаётся внешним условием

В текущей облачной среде URL, публичный ключ и серверное подключение Supabase настроены. Приложения Google/GitHub/VK/Яндекс и их OAuth-секреты владельцем пока не подключены. Создать их без доступа к кабинетам провайдеров невозможно. Пошаговая конфигурация и диагностика аватаров: [AUTH-LAUNCH](AUTH-LAUNCH.md). Исторические результаты тестов ниже относятся к первоначальному обновлению, текущие результаты фиксируются в CHECKPOINT.md.

Полный `npm run check` и `npm run test:ui` выполняются локально в изолированных тестах. Браузерная проверка добавляет тёмную тему, загрузку шрифта, читаемость и отсутствие горизонтального переполнения на 1440×640, 1024×600, 390×844 и 320×568. Отдельно проверяется настоящий `next dev` без перекрывающего индикатора. Платежи, командный доступ, уведомления Telegram и прежние внешние зависимости из MVP-LAUNCH не становятся готовыми от изменения темы или OAuth-кнопок.
