# LEADLY на Vercel: запуск и подключение Google

## Подготовленная конфигурация

- Актуальная ветка: `leadly-mvp-download` репозитория `Egor-Sabanov/leadly-project`. `main` пока не обновлялась и не является этой версией продукта.
- Node.js 24.x закреплён в package.json и lockfile. Framework Preset — Next.js, Root Directory — корень репозитория.
- `vercel.json` задаёт `npm ci --include=dev` (TypeScript нужен для проверки до сборки) и `npm run check:readiness && npm run build`. Проверка читает backend, не меняет данные и не отправляет письма. Отказ базовых подключений прерывает сборку; отсутствие включённого Google пока отмечается отдельно как pending.
- `.vercelignore` исключает локальные env-файлы, зависимости/сборки, результаты тестов и документацию из загрузки CLI. Реальные настройки задаются в Vercel, а не загружаются из облачного `.env.local`.
- Cookies Supabase на HTTPS/Vercel получают Secure, сохраняют SameSite=Lax, путь `/` и доступ браузерного SDK. HTTP localhost продолжает работать для разработки. Идентичности аккаунтов не объединяются приложением самостоятельно.
- Расписание импорта, Telegram и реальные платежи этой конфигурацией не включаются.

## Подключение кабинета

В этой среде установлен официальный Vercel CLI 64.5.0 вне исходников. Первоначально `whoami` подтвердил отсутствие авторизованного аккаунта, затем выполнен официальный вход через device flow. Последующий `whoami` и запрос команд подтвердили аккаунт egor-sabanov. Проект leadly создан в одноимённом scope; другие проекты не менялись. Пароль и access token в чат не передаются. Одноразовая ссылка может истечь; новый код выдаёт CLI только после возобновления подключения. Подтверждённый вход не равен выполненному развёртыванию.

Проект создан и связан через игнорируемый `.vercel/project.json`. Назначен адрес `https://leadly-topaz-seven.vercel.app`, но назначение домена не означает готовое приложение. Node 24.x, публичные Supabase URL/key и LEADLY_SITE_URL уже добавлены. Серверный секрет владелец добавляет в https://vercel.com/egor-sabanov/leadly/settings/environment-variables для Production. После этого можно загрузить именно проверенную рабочую версию через CLI. Перед загрузкой обязательно проверить `vercel whoami`, имя и scope проекта, затем серверные настройки. Не использовать неопознанную команду/чужую командную учётную запись и не менять платёжный план автоматически.

При импорте через Git Vercel по умолчанию выбирает main. Для этой версии в **Settings → Environments → Production → Branch Tracking** нужно указать `leadly-mvp-download`. После этого **Deployments → Create Deployment** позволяет указать эту ветку или конкретный проверенный commit. Не принимать автоматически первый deployment из старой main за готовый LEADLY. Официальная инструкция: https://vercel.com/docs/git#production-branch .

## Настройки Vercel, которые задаются владельцем один раз

| Переменная | Где нужна | Значение |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Build и Runtime | HTTPS URL своего проекта без `/rest/v1` |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Build и Runtime | Публичный publishable key этого же проекта |
| `SUPABASE_SERVICE_ROLE_KEY` | Только сервер | Серверный секрет того же Supabase для приватных аватаров и служебных операций |
| `LEADLY_SITE_URL` | Runtime | Точный стабильный HTTPS origin приложения, когда Vercel выдаст адрес |

Секрет Supabase вводится в защищённые **Project Settings → Environment Variables** Vercel. Его нельзя делать `NEXT_PUBLIC_*`. Прокси-привязка секрета в облачном чате не переносится автоматически на Vercel; нельзя загружать её placeholder как настоящий ключ. Обычным пользователям никакие ключи не нужны.

До получения стабильного адреса `LEADLY_SITE_URL` можно оставить незаданным: первый запуск использует адрес текущего запроса. После назначения домена необходимо задать точный HTTPS origin и выполнить повторное развёртывание. Не задавать localhost на Vercel: новая проверка остановит сборку. Для рабочих проверок использовать production domain, а не временный адрес другой preview-ветки. Тариф хостинга выбирает владелец с учётом условий сервиса и коммерческого использования.

## Проверка после развёртывания

```bash
npm run check:deployment -- https://АДРЕС-ПРИЛОЖЕНИЯ
```

Команда только читает публичные маршруты, не следует OAuth-переходу, не создаёт аккаунты и не отправляет письма. Она проверяет:

- открытие /auth и /privacy, заголовки и отсутствие общего кеширования авторизации;
- перенаправление гостя с / и /profile на вход того же сайта;
- HTTP 401 личных API без сессии;
- безопасное возвращение при ошибке callback и отказе провайдера;
- запрет произвольного провайдера и доставку статического файла Next.js;
- у включённого Google — точный Supabase, PKCE, verifier cookie и callback этого сайта.

`transportReady=true` не означает настоящий вход у Google, доставку email или проверенную загрузку аватара на этом хостинге. `realUserSignInVerified` остаётся false, поскольку команда не входит за владельца. Если Google выключен, он остаётся pending. Публичная проверка пока невозможна без созданного проекта/адреса; на внутренней production-сборке команда проверена отдельно с явным `--local`.

Для Vercel с Deployment Protection проверка может получить страницу входа Vercel вместо LEADLY. В таком случае нужно выбрать правильный production URL или предоставить поддерживаемый доступ к deployment, а не отключать TLS.

## Google после появления адреса

1. В Google Cloud создать OAuth client типа Web Application и настроить consent screen/тестовую аудиторию.
2. Callback у Google: `https://leezcyaqhozguvcehcpd.supabase.co/auth/v1/callback`.
3. Client ID и Client Secret сохранить в Supabase Authentication → Sign In / Providers → Google, включить Google.
4. В Supabase URL Configuration задать HTTPS Site URL приложения и разрешить точные `https://АДРЕС-ПРИЛОЖЕНИЯ/auth/callback` и `https://АДРЕС-ПРИЛОЖЕНИЯ/auth/callback?next=/auth/reset`.
5. Повторить `check:deployment`, затем выполнить настоящий вход с разрешённым Google-аккаунтом, отказ от входа, повторный вход, ознакомление, профиль, фото и выход на компьютере и телефоне. Проверить также подтверждение email и восстановление.

Настройки провайдера не создаются из серверного ключа Supabase. Подробнее: [AUTH-LAUNCH](AUTH-LAUNCH.md).
